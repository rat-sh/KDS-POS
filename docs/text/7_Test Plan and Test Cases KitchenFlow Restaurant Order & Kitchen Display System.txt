  1. Introduction

  1.1 Purpose
  This is document 7 of 7. It defines how KitchenFlow is shown to work: the strategy, the
  environments and data, the test cases (what to do and what must happen), the pass
  criteria, and the trace from every requirement to the tests that prove it. It also closes the
  document set: section 17 gathers the changes that documents 3 to 6 proposed to earlier
  documents into one register, so nothing is lost.


  1.2 Scope
  In scope: the backend, the database, the REST and streaming API, and the deployed stack
  (Compose and Nginx). The screens are covered only where a requirement states a
  behaviour (timing, readability, the demo). Out of scope: third-party penetration testing,
  multi-outlet operation, and real payment gateways.


  1.3 How to use this document
  The plan lives here; the executable tests live in the repository, and every test method
  carries its case ID in its name (LLD 6.4). A case lists the requirement IDs it proves, so a
  failing test points straight back to a requirement and a passing suite can be traced
  forward to coverage.

  2. Test strategy

  2.1 Objectives
     1. Prove the correctness invariants under concurrency: no duplicate, lost, oversold or
        stuck orders (SRS goal G1).
     2. Prove the API contract, including every error case in the API document.
     3. Prove real-time behaviour and recovery: screens update within 1 second and heal
        after a disconnect.
     4. Prove protection and resilience: access control, limits, overload and fault behaviour.
     5. Keep the proof cheap enough to run on every commit, and honest: each protection
        has a mutation variant that must fail when the protection is removed.

  2.4 Principles
         Test first. Each build step in LLD section 7 begins with its failing tests.
         Deterministic. No Thread.sleep: asynchronous assertions use Awaitility with a
         timeout. Time comes from a controllable Clock; random data uses fixed seeds; bucket
         refill uses an injected time meter.
         Independent. Each test builds the data it needs and never relies on another test's
         leftovers or on execution order.
         Real database. Integration tests run the real Flyway migration, the real roles and real
         constraints; the database is never mocked.
         Prove the protection. For each lock, constraint or compare-and-set that exists for
         correctness there is a variant with it removed, and the test must then fail (LLD 6.2).
         Flaky means broken. A test that fails intermittently is a defect in the test or in the
         code. It is fixed within 2 working days or deleted; it is never retried until green.

  2.7 Metrics and reporting
  At the end of each phase, one page: tests run and passed per family; line coverage of
  service and domain code (JaCoCo); requirement coverage from section 15; concurrency
  repeat results (failures must be zero); mutation variants that failed as intended;
  performance numbers against thresholds; open defects by severity. The same numbers
  decide the release criteria in 2.5.


  2.8 Roles
  One developer writes code and tests. A reviewer (a senior, a friend or a mentor) reads this
  plan, the concurrency tests and the demo script, and watches one full acceptance run.
  Before each merge the developer applies a self-review checklist: tests first, case IDs in
  names, no sleeps, no shared data, every new endpoint in the role table and the case files.

  3.4 Time, randomness and configuration
         A MutableClock bean replaces the system clock in the test profile and can be
         advanced, so lockout windows, the recall window, token expiry and the business-day
         cutoff are tested without waiting.
         Rate-limit buckets take an injected time meter, so refill is tested instantly (RL-01).
         The test profile shortens intervals that are fixed in production: the stream heartbeat
         (200 ms) and token lifetime. This needs the sse heartbeat to be a configuration
         property (change 14 in section 17).
         Generators and load scripts use fixed seeds, so a failure can be reproduced.

  3.5 Accounts, secrets and artefacts
  Test users and passwords come from the TestData builders and the test profile; the JWT
  key in tests is a constant that is never used elsewhere. No real secret appears in the
  repository (SC-15). Every run keeps its reports as build artefacts: surefire and failsafe
  results, the JaCoCo report, k6 summaries, and the saved EXPLAIN plans.

  6. API contract and integration tests

  6.1 Case source and format (CT)
  Every row of every case table in the API document is one test. Its ID is the endpoint ID
  plus the row number in that endpoint's case table, counted from 1 in document order: O-
  01.14 is the fourteenth row of the O-01 table. The cases live in YAML files, one per
  endpoint, under src/test/resources/cases. A generic runner (a JUnit TestFactory) builds
  the fixtures, sends each request to the running application with RestAssured, and checks
  the response and the database. The expected values are copied from the API document; a
  change to a case table and the matching YAML change in the same commit.

     endpoint: O-01
     cases:
         - id: O-01.09
           title: item unavailable
             given:
                 users: [ cashier1 ]
                 items:
                   - { name: Cola, price: '69.00', gst: '18.00', stations: [ Beverage ],
     available: false }
             request:
                 as: cashier1
                 method: POST
                 path: /orders
                 body:
                     orderType: TAKEAWAY
                     lines: [ { itemId: '$item.Cola', quantity: 1 } ]
             expect:
                 status: 422
                 code: ITEM_UNAVAILABLE
                 errors: [ { field: 'lines[0].itemId', code: ITEM_UNAVAILABLE } ]
             post:
                 orders: 0
                 stock: unchanged
                 audit: none


  Symbolic references such as $item.Cola, $user.cashier1 and $order.first are resolved by
  the runner. A row marked n/a in the API tables (a race between two requests) has no
  YAML case of its own; its entry points to the concurrency case that covers it, for example
  see: CC-05.

         Errors: the whole envelope (timestamp, status, code, message, path, correlationId,

  7. Concurrency and mutation tests
  These tests are the heart of the project: they prove the claims of SAD section 6 about
  duplicates, overselling and stuck orders. Rules for all of them:

          A shared helper releases the threads together with a latch (LLD 6.2). Each thread
          uses its own user so the per-user rate limits (30 order writes a minute) do not
          interfere; the test profile also raises the limits.
          Every case runs 50 times in the nightly build and 5 times on each commit. The failure
          budget is zero: a single failure in 50 is a defect.
          Waiting uses Awaitility with a 30-second timeout and never sleeps.
          After each case the consistency queries C1 to C7 must return zero rows.
          A mutation variant (marked m) removes one protection through a seam or a scratch
          schema and must make its test fail, which proves the test can see the bug.
