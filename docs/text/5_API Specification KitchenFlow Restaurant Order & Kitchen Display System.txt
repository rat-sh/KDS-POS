  1. Introduction

  1.1 Purpose
  This document is the contract of the KitchenFlow REST and server-sent-events API: every
  endpoint, its roles and limits, request and response schemas, validation rules, and every
  success, error and edge case a client can meet. It is document 5 of 7. It implements SRS
  sections 5 and 10, SAD sections 5, 6 and 9 and DBD sections 5 and 8. The OpenAPI
  definition is generated from the code (FR-SYS-02); this document is what that generated
  definition and the contract tests are checked against.


  1.2 Scope and audience
  In scope: the web clients (cashier POS, station boards, manager board, status board,
  admin screens), a future Android kitchen display, test authors and reviewers. Out of
  scope: internal Java interfaces and the database.


  1.3 How to read this document
  Endpoints have IDs such as O-01 (section 4 lists them all). Priorities are M, S and C as in
  the SRS. A feature marked (proposed) is added by this document and listed in section 17.2
  for the SRS change control. Examples are illustrative: ids and timestamps vary. Every
  endpoint section ends with a table of its cases, so a test author can derive one test per
  row.

  2. API conventions

  2.1 Protocol and formats

     Topic                        Rule

     Base path                    /api/v1 on the Nginx host. A breaking change would introduce /api/v2 and
                                  run both until clients have moved; additive changes (new optional fields,
                                  new endpoints) stay in v1.

     Media types                  application/json (UTF-8) for requests and responses; text/event-stream for
                                  streams; text/csv for report exports (Could); application/pdf for the
                                  printable bill (Could). A body with another Content-Type returns 415; an
                                  unsatisfiable Accept returns 406.

     Methods                      GET never changes state. POST creates or performs an action. PUT
                                  replaces. PATCH changes only the fields sent. DELETE removes. Any other
                                  method returns 405 with an Allow header.

     Naming                       JSON fields in camelCase, enum values in UPPER_SNAKE_CASE, paths in
                                  lowercase kebab-case.

     Identifiers                  Numeric 64-bit integers, always below 2^53 so JavaScript reads them
                                  exactly. Order numbers (KF-YYYYMMDD-NNNN, four or more digits) are
                                  display values, searched by query parameter and never used in paths.

     Money                        JSON strings with exactly two decimals, for example 513.72, never JSON
                                  numbers. A money field sent as a number returns 400; one with other than
                                  two decimals returns 422 INVALID_SCALE. GST rates are strings with two
                                  decimals, for example 5.00.

     Date and                     Instants are ISO 8601 in UTC with milliseconds and a Z suffix. A business
     time                         day is a date, YYYY-MM-DD. Clients display time in Asia/Kolkata.

     Strings                      Leading and trailing whitespace is trimmed. A required string that is blank
                                  after trimming counts as missing. Control characters are rejected
                                  (INVALID_CHARACTERS). Lengths count characters; passwords count
                                  bytes.

     Nulls                        Responses always include every documented field; an absent value is null.
                                  In requests a missing required field and an explicit null are both REQUIRED.
                                  PATCH changes only the fields present.

  2.2 Authentication
        Every endpoint except those marked Public needs a bearer JWT in the Authorization
        header. The access token lives 15 minutes and holds sub (user id), role, stations (ids),
        jti, iat and exp. It carries no personal data.
        401 UNAUTHENTICATED, with a WWW-Authenticate: Bearer header, when the token is
        missing, malformed, wrongly signed or expired. 403 FORBIDDEN when the user is
        authenticated but the role or station binding does not allow the call.
        Deactivating a user stops login and refresh at once; an access token already issued
        stays valid until it expires, at most 15 minutes (FR-AUTH-05).
        Refresh token (Should): cookie kf_refresh, HttpOnly, Secure, SameSite=Strict, path
        /api/v1/auth, lifetime 8 hours (configurable), rotated on every use. Endpoints that read
        the cookie also check the Origin header against the CORS allow-list and return 403 on
        a mismatch.

  Every request meets the same checks in the same order, so the first failing check decides
  the response.

     1            Edge limits at Nginx: request size, connections,         413, 429
                  per-address rate

     2            Syntax: method, Content-Type, Accept, JSON               405, 415, 406, 400
                  parsing, unknown properties and parameters,
                  value types

     3            Authentication                                           401

     4            Application rate limit for the user and endpoint         429
                  class

     5            Authorization: role, then station binding                403

     6            Lookup of resources named in the path                    404

     7            Field validation; all violations are collected and       422

     8            Idempotency check (POST /orders): replay or key          Replay, 422

  Two consequences. Role checks come before lookups, so a Kitchen user calling an order
  endpoint gets 403 even for an id that does not exist. Unknown paths return 404 only after
  authentication.

         Page parameters: page (starting at 0, default 0), size (1 to 100, default 20) and sort as
         field,asc or field,desc. Each endpoint lists its sortable fields and default; ties are
         broken by id.
         List envelope: content (array) and page with number, size, totalElements and
         totalPages.

        Cursor variant (orders and audit): send cursor with the opaque value from the previous
        response and size; the response carries content and nextCursor (null on the last page)
        and omits totals. Sort is fixed (newest first). Combining cursor with page returns 400.

  2.7 Idempotency
  POST /orders accepts an Idempotency-Key header: 1 to 80 characters from letters, digits,
  underscore and hyphen; a UUID v4 is recommended. The header is optional, but a request
  without it cannot be retried safely. Scope is per user and retention is 24 hours (BR-15, FR-
  ORD-10).


     Situation                                                                Result

     First use of the key                                                     Processed normally; the response is stored
                                                                              with the key

     Same key and identical payload, first                                    The original status and body are replayed with
     request finished                                                         Idempotency-Replayed: true; no new order

     Same key arrives while the first request is                              The duplicate waits (up to the 2-second lock
     still running                                                            timeout), then replays. If the first fails and rolls
                                                                              back, the duplicate is processed as a first use

     Situation                                                             Result

     Same key, different payload                                           422 IDEMPOTENCY_KEY_REUSED; nothing is
                                                                           created

     First request failed with 4xx or 5xx                                  Nothing was stored; a retry runs again

     More than 24 hours later                                              The key is forgotten and reuse creates a new
                                                                           order, so never reuse a key

     Malformed key                                                         422 VALIDATION_FAILED with field
                                                                           Idempotency-Key, code INVALID_FORMAT


  Payload identity is the SHA-256 of the canonical JSON body (keys sorted, whitespace
  removed), so field order does not matter. A replay returns the original snapshot, not the
  order's current state; clients fetch the order for that. Other endpoints ignore the header
  and rely on state checks instead.


  2.8 Optimistic concurrency
  Representations of orders, tickets, menu items, users and stock carry a version. Mutating
  requests marked expectedVersion must send the version the client last saw. A mismatch
  returns 409 STALE_VERSION with the current representation in details.current. The client
  re-reads, re-applies its intent and retries; it never retries blindly.

  A second form of conflict is an action that was already applied (a double tap, or two
  people acting together). It returns 409 INVALID_TRANSITION whose
  details.currentStatus already equals the target state. Clients treat that case as success
  for start, bump, cancel and complete.


  2.9 Caching and conditional requests
  Only GET /menu is cacheable: it returns an ETag built from the menu version and a hash of
  the filters, with Cache-Control: no-cache. A request with a matching If-None-Match
  returns 304 with no body. Every other authenticated response is Cache-Control: no-store.

  Two layers apply (SAD 5.2). Nginx limits each address coarsely; the application limits each
  user by endpoint class with token buckets. The class of every endpoint is in section 4.

  Open streams are also capped at 3 per user, 20 per address and 50 in total. A rejected
  request returns 429 RATE_LIMITED with Retry-After and details.rateClass. Clients wait at
  least Retry-After, add random jitter, and never retry a write without its Idempotency-Key.
  Many devices behind one address share the address-keyed limits: status boards should
  use the stream and, if they poll, no faster than every 3 seconds.


  2.11 CORS and transport
  HTTPS outside local development. CORS allows only configured origins, the methods GET,
  POST, PUT, PATCH, DELETE and OPTIONS, and the request headers Authorization,
  Content-Type, Idempotency-Key, If-None-Match and X-Correlation-Id. Exposed response
  headers: X-Correlation-Id, ETag, Retry-After, Idempotency-Replayed and the X-RateLimit
  headers. Preflight answers are cached for 600 seconds. Credentials (the refresh cookie)
  are allowed only on the auth endpoints.

  15. Cross-cutting cases

  15.1 Typical call sequences
  A. Start of shift. A-01 login, A-04 me, S-01 stations, M-01 menu (keep the ETag). A kitchen
  screen then opens K-01 and X-01.

  B. Counter order, happy path.

   1. M-01 with If-None-Match to refresh the menu.
   2. O-01 with a new Idempotency-Key.
   3. P-01 payment; P-03 for the bill.
   4. Kitchen screens receive TICKET_CREATED on X-01; each station calls K-03 and then K-
      04.
   5. After the last bump the order is READY and the token moves to READY on B-01 and X-
        03.
   6. O-06 when the food is handed over.

  C. Cancellation. O-05 by the Cashier before payment; after payment only a Manager can
  cancel.

  D. Mistaken bump. K-05 within the recall window.

  E. Token expires mid-shift. Any call returns 401: refresh with A-02 (or log in again), retry
  the call and reconnect the streams.

  F. Network failure while creating an order. Retry O-01 with the same Idempotency-Key.
  Never generate a new key for the same attempt.

  G. Network failure while paying. Call P-02: 200 means the payment succeeded; 404
  means retry P-01.

  H. An item sells out. O-01 returns 409 OUT_OF_STOCK; the screen reloads M-01. I. A
  Manager marks an item unavailable (M-17). Cashiers see it on their next M-01.
