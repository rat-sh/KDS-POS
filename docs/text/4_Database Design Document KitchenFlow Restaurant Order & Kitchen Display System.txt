  1. Introduction

  1.1 Purpose
  This document specifies the PostgreSQL schema of KitchenFlow at DDL level: tables,
  columns, types, constraints, indexes, roles, the concurrency-critical SQL, volumes, seed
  data and migrations. It is document 4 of 7. It implements the data requirements in SRS
  section 9 (DR-01 to DR-09) and the concurrency and data architecture in SAD sections 6
  and 8. The SQL in section 5 is the content of the baseline migration V1 in executable form.


  1.2 Scope
  One database, kitchenflow, with one schema, kf, holding 26 tables. Out of scope: an outlet
  identifier for multi-outlet operation (a scale-out change described in SAD 5.6), customer
  personal data (none is stored), and anything outside PostgreSQL.

  3. Table map
  The schema has 26 tables owned by eight modules (SAD section 4.1), grouped as in Figure
  1. Foreign keys cross a module boundary only in the directions the dependency rules
  allow: order to menu, payment to order, kitchen to order, inventory to menu, and every
  module to station (config) and to user ids (auth). One change from SAD 4.1: station is
  owned by config, because menu, kitchen and auth all reference it. audit_event has no
  foreign keys (DD-11).

  4. Roles, schema and session settings
  Three things are created once, outside the migrations: the roles, the schema and the
  session limits of the application role (SAD 5.4 and 8.1). Flyway connects as kf_migrator;
  the application connects as kf_app.

     -- Run once by the Compose init script as a superuser. Passwords arrive as
     psql variables
     -- taken from environment variables; the repository contains none.
     CREATE ROLE kf_migrator LOGIN PASSWORD :'migrator_password';
     CREATE ROLE kf_app      LOGIN PASSWORD :'app_password';
     CREATE DATABASE kitchenflow OWNER kf_migrator;


     -- Then, connected to the kitchenflow database:
     CREATE SCHEMA kf AUTHORIZATION kf_migrator;
     REVOKE ALL ON SCHEMA public FROM PUBLIC;
     GRANT USAGE ON SCHEMA kf TO kf_app;


     ALTER DEFAULT PRIVILEGES FOR ROLE kf_migrator IN SCHEMA kf
       GRANT SELECT, INSERT, UPDATE ON TABLES TO kf_app;
     ALTER DEFAULT PRIVILEGES FOR ROLE kf_migrator IN SCHEMA kf
       GRANT USAGE, SELECT ON SEQUENCES TO kf_app;


     ALTER ROLE kf_app SET search_path = kf;
     ALTER ROLE kf_app SET timezone = 'UTC';
     ALTER ROLE kf_app SET statement_timeout = '5s';
     ALTER ROLE kf_app SET lock_timeout = '2s';
     ALTER ROLE kf_app SET idle_in_transaction_session_timeout = '30s';


       kf_app can read, insert and update every table. It receives DELETE only where section
       5.11 grants it, and it has no schema-change rights.
       Role settings apply to new sessions. Report queries raise the limit for their own
       transaction with SET LOCAL statement_timeout = '10s'.
       Passwords come from environment variables at container start.

            sum(o.total)     AS total

     WHERE o.business_day BETWEEN :from AND :to AND o.status <> 'CANCELLED'
     GROUP BY o.business_day, p.method, o.order_type
     ORDER BY o.business_day, p.method, o.order_type;

  10.6 Performance dataset generator (FR-CFG-03)
       Parameters: 180 days ending yesterday, 100,000 orders, a fixed random seed so every
       run is identical. It refuses to run on a database that already holds orders unless a reset
       flag is given.
       Timing: hour-of-day weights peak at 12 to 14 and 19 to 21; weekends carry 1.3 times the
       weekday weight. The business day follows the 04:00 cutoff and tokens run in time
       order within each day.
       Content: 1 to 4 lines per order (mean about 2.5), quantity 1 to 3, items weighted so the
       top 10 account for about 60 percent, modifiers on about 40 percent of lines. Prices,
       GST and totals use the same formulas as the application, so every CHECK passes.
       Outcomes: 97 percent COMPLETED and 3 percent CANCELLED (cancelled in
       CREATED, with no payment). Payment mix 50 percent UPI, 30 percent CARD, 20
       percent CASH.
       Tickets: one per distinct station among the order's items (about 2 per order). Cycle
       time is the target times a random factor between 0.6 and 1.6, so about 12 percent of
       tickets are late.
       Audit: five events per order (created, paid, in kitchen, ready, completed), giving at
       least 500,000 rows (NFR audit search target).
       Mechanics: set-based INSERT ... SELECT with generate_series, ids from the
       sequences, run as kf_migrator in one transaction, followed by ANALYZE. Target: under
       2 minutes on the reference laptop.
       Checks after loading: row counts, and the consistency queries C1 to C7 in section 14.2
       all return zero rows.

  11.2 Baseline strategy
  While the schema is still changing, V1 is replaced wholesale rather than patched. A
  developer resets the local database (docker compose down -v) whenever V1 changes,
  and CI always applies V1 to an empty database. When the first demo build is cut, V1 is
  frozen and tagged.


  11.3 After the first demo
       Changes are forward-only migrations (V2, V3 and so on). An applied migration is never
       edited; Flyway's checksum validation fails the build if it is.
       Breaking changes use expand and contract: add a nullable column, deploy code that
       writes both, backfill, add the constraint as NOT VALID and then VALIDATE it, and drop
       the old column in a later migration.
       Large index builds use CREATE INDEX CONCURRENTLY in a migration marked as non-
       transactional.
       Rollback means redeploying the previous image and restoring the dump taken before
       the migration. Every migration pull request carries a one-line rollback note.

  12. Backup, retention and maintenance
       Backup: a nightly pg_dump in custom format, keeping 7 daily copies. A weekly restore
       drill loads the latest dump into a scratch database and runs the consistency queries
       (section 14.2) and a row-count comparison.
       Retention: orders and audit records are kept for at least 12 months (DR-09). The only
       purges are idempotency_record rows older than 24 hours and refresh_token rows that
       expired more than 7 days ago. They run as scheduled jobs in batches of 1,000 rows so
       transactions stay short, as kf_app, which holds DELETE on exactly those tables.
       Vacuum and statistics: autovacuum stays on with the per-table settings in section 5.11.
       Run ANALYZE after any bulk load. Watch pg_stat_user_tables and investigate when
       dead tuples exceed 20 percent of a hot table.
       Statement statistics: enable pg_stat_statements in the Compose PostgreSQL image
       and review the slowest statements once during the hardening phase (OI-05).
       Connections: PostgreSQL's default of 100 connections is far above the application pool
       of 20 (SAD 5.4), leaving headroom for the migrator, backups and manual sessions.
       Time zone: the server and the application role run in UTC.

  14.2 Consistency queries
  Each query returns zero rows on a healthy database. They run after the generator, in the
  weekly restore drill, and as a scheduled check in the polish phase.

     -- C1 Order totals equal the sum of their lines
     SELECT o.id FROM kf.orders o
     JOIN kf.order_line l ON l.order_id = o.id
     GROUP BY o.id, o.subtotal, o.tax_total
     HAVING o.subtotal <> sum(l.line_subtotal) OR o.tax_total <> sum(l.line_tax);


     -- C2 Every order past CREATED has a payment
     SELECT o.id FROM kf.orders o
     LEFT JOIN kf.payment p ON p.order_id = o.id
     WHERE o.status IN ('PAID','IN_KITCHEN','READY','COMPLETED') AND p.id IS NULL;


     -- C3 A READY or COMPLETED order has no open ticket
     SELECT o.id FROM kf.orders o
     JOIN kf.ticket t ON t.order_id = o.id
     WHERE o.status IN ('READY','COMPLETED') AND t.status IN
     ('NEW','IN_PROGRESS');


     -- C4 An IN_KITCHEN order has at least one ticket
     SELECT o.id FROM kf.orders o
     WHERE o.status = 'IN_KITCHEN'
       AND NOT EXISTS (SELECT 1 FROM kf.ticket t WHERE t.order_id = o.id);


     -- C5 Tickets mirror their order's rush flag and business day (DD-09)
     SELECT t.id FROM kf.ticket t JOIN kf.orders o ON o.id = t.order_id
     WHERE t.rush <> o.rush OR t.business_day <> o.business_day;

     -- C6 Every menu item has at least one station (BR-09)
     SELECT i.id FROM kf.menu_item i
     WHERE NOT EXISTS (SELECT 1 FROM kf.item_station s WHERE s.item_id = i.id);


     -- C7 Tokens have no gaps within a business day (a rolled-back order must not
     consume one)
     SELECT business_day FROM kf.orders
     GROUP BY business_day
     HAVING max(token) <> count(*);
