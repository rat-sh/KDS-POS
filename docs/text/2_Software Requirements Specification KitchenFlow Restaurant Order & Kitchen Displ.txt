  1. Introduction

  1.1 Purpose
  This document specifies what KitchenFlow shall do and how well it shall do it. It is
  document 2 of 7 and the contract between the product idea (document 1) and the design
  documents (3 to 6): every design element and every test must trace back to a
  requirement ID in this document.


  1.2 Scope
  KitchenFlow is a web-based order and kitchen-display system for one quick service
  restaurant (QSR) outlet. It covers counter order entry with pricing and GST, simulated
  payment recording, automatic routing of items to kitchen stations, a real-time kitchen
  display with start, bump and recall, a customer status board, lightweight inventory, an
  audit trail and management reports.

  Out of scope for version 1: real payment gateways, delivery-aggregator integrations, multi-
  outlet or multi-tenant operation, printer or POS hardware integration, customer accounts
  and personal data, demand forecasting and machine learning, and native mobile apps.


  1.3 Intended readers
  The developer (implementation and testing), reviewers and interviewers (to judge
  engineering depth), and anyone writing the later documents.


  1.4 Conventions
        IDs: FR-MODULE-nn functional requirement; BR-nn business rule; NFR-CATEGORY-nn
        quality requirement; AT-nn acceptance scenario; OI-nn open issue.

  2. Overall description

  2.1 Product perspective
  KitchenFlow is a new, self-contained system built as a modular monolith. Clients are web
  screens (cashier POS, kitchen station boards, manager board, customer status board,
  admin screens) that talk to one REST and server-sent-events API backed by a relational
  database. Version 1 has no integration with external systems.

  2.3 Operating environment
        Server: Java 17 or newer (Java 21 preferred) on Windows, Linux or macOS, or in a
        Docker container.
        Database: PostgreSQL 15 or newer (MySQL 8 is an acceptable alternative; the choice is
        closed in document 3).
        Clients: current Chrome, Edge or Firefox on a desktop or a 10-inch landscape tablet, on
        the same local network as the server.


  2.4 Design and implementation constraints
        Java, Spring Boot and SQL are fixed by the project's purpose.
        All money arithmetic uses decimal types, never floating point.
        Every state-changing operation is transactional and audited.
        The system stores no customer personal data.
        One developer and a fixed time budget, so the Must list is protected first.


  2.5 Design-basis workload
  One outlet, 800 to 1,500 orders per day, a peak of about 150 orders per hour, up to 5 station
  screens, 10 staff users at once and 1 status board. The load tests in section 8 deliberately
  exceed this peak.

  4. Business rules

     ID             Rule

     BR-01          Token numbers are unique within a business day,
                    start at 1, increase by one per order and restart at
                    the business-day cutoff (BR-16).

     BR-02          All money uses decimal arithmetic in INR with two
                    decimals. Each order line stores a snapshot of the
                    unit price and GST rate used, so later menu
                    changes never alter existing orders.

     BR-03          GST per line = (unit price plus selected modifier
                    prices) x quantity x category rate, rounded half-up
                    to two decimals. Order total = sum of line amounts
                    plus line GST. Menu prices are exclusive of GST
                    (see OI-05).

     BR-04          An unavailable or inactive item cannot be added to
                    an order. Orders already created are unaffected.

     BR-05          A CREATED order may be cancelled by a Cashier or
                    Manager. An IN_KITCHEN order may be cancelled
                    by a Manager only. READY and COMPLETED
                    orders cannot be cancelled. A reason is always
                    required.




                                                                                                                         Page 5 of 35
Software Requirements Specification: KitchenFlow Restaurant Order & Kitchen Display System




     ID             Rule

     BR-06          An order is READY exactly when all of its non-
                    cancelled tickets are DONE. Recalling a ticket of a
                    READY order returns the order to IN_KITCHEN.

     BR-07          Payment is taken before the kitchen sees the order
                    (pay first). Partial and split payments are not
                    supported in version 1.

     BR-08          The payment amount must equal the order total.

     BR-09          Every item maps to at least one station. An item
                    mapped to several stations appears on the ticket
                    of each of those stations. A combo has no station
                    of its own; each component routes to its own
                    stations.

     BR-10          Station queues are ordered by RUSH first, then by
                    payment time, oldest first.

     BR-11          Ticket colour: green until 80 percent of the target
                    time has elapsed, amber from 80 to 100 percent,
                    red beyond 100 percent. A ticket's target is the
                    longest target time among its items. Thresholds are
                    configurable.

     BR-12          Stock is reserved when an order is created and
                    restored when the order is cancelled while
                    CREATED. Cancelling an IN_KITCHEN order does
                    not restore stock (treated as wastage). An item
                    with tracked stock becomes unavailable at zero.

     BR-13          Every state change, payment, price change,
                    availability change and user or role change creates
                    an audit record in the same transaction.

     BR-14          An order can be edited only while CREATED.

     BR-15          A request that repeats an Idempotency-Key within
                    24 hours with an identical payload returns the
                    original response. With a different payload it is
                    rejected with 422 IDEMPOTENCY_KEY_REUSED.

     ID             Rule

     BR-16          The business day runs from the configured cutoff
                    (default 04:00, Asia/Kolkata) to the next cutoff.
                    Tokens and reports use the business day.

     BR-17          A DONE ticket can be recalled only within the
                    configured recall window (default 10 minutes) and
                    only while its order is not COMPLETED.

     BR-18          Timestamps are stored in UTC and displayed in
                    Asia/Kolkata.
