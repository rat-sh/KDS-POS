  1. Introduction

  1.1 Purpose
  This document turns the architecture (SAD), the schema (DBD) and the API contract
  (API) into class-level design: the package layout, the classes of every module with their
  responsibilities and key signatures, the algorithms of the risky operations, how errors,
  security, rate limiting, caching, events and streams are built, and an ordered build plan. It
  is document 6 of 7, and it is written so that you can code from it. The code blocks are Java
  21 skeletons: they show structure and the critical lines, not every import, getter or trivial
  CRUD method.


  1.2 Scope
  The backend only. The React screens follow the API and are outside the seven documents.
  Technology: Spring Boot 3, Spring Security (resource server), Spring Data JPA with
  Hibernate, JdbcTemplate for native statements and reports, Flyway, Caffeine, Bucket4j
  and Micrometer.

  3.1 Money
  Money is a value object over BigDecimal with scale 2 (DD-04, BR-02). Rounding is
  HALF_UP, which matches the database's round(numeric, 2) for the non-negative amounts
  used here, so Java and the CHECK constraints in DBD 5.7 always agree.

     public record Money(BigDecimal amount) implements Comparable<Money> {
         private static final BigDecimal HUNDRED = BigDecimal.valueOf(100);
         public static final Money ZERO = new Money(new BigDecimal("0.00"));


         public Money {                                            // compact
     constructor
             Objects.requireNonNull(amount);
             if (amount.scale() != 2) throw new IllegalArgumentException("Money
     needs scale 2: " + amount);
         }
         public static Money parse(String text) { return new Money(new
     BigDecimal(text)); }
         public static Money round(BigDecimal v) { return new Money(v.setScale(2,
     RoundingMode.HALF_UP)); }


         public Money plus(Money o)   { return new Money(amount.add(o.amount)); }
         public Money minus(Money o) { return new
     Money(amount.subtract(o.amount)); }
         public Money times(int qty) { return new
     Money(amount.multiply(BigDecimal.valueOf(qty))); }
         public Money percent(BigDecimal rate) {                   // BR-03: GST
     on one line
             return round(amount.multiply(rate).divide(HUNDRED)); // dividing by
     100 always terminates
         }
         @Override public int compareTo(Money o) { return
     amount.compareTo(o.amount); }
         @Override public String toString() { return amount.toPlainString(); }
     }


  On the wire Money is a JSON string (API 2.1). MoneyJson has a serializer that writes
  toString() and a deserializer that accepts only a string token: a number is rejected as a
  type mismatch (400), a string with other than two decimals fails with INVALID_SCALE
  (422), and any other text with INVALID_FORMAT. A signed variant of the deserializer,
  selected with @JsonDeserialize on priceDelta fields, allows a leading minus.

         private static final ZoneId IST = ZoneId.of("Asia/Kolkata");
         private final Clock clock;
         private final ConfigService config;


         public LocalDate businessDayOf(Instant at) {
             ZonedDateTime local = at.atZone(IST);

     spring:

           deserialization:

               write-dates-as-timestamps: false

  InstantMillisSerializer formats with the pattern yyyy-MM-dd'T'HH:mm:ss.SSS'Z' in UTC,

  REQUIRED. The custom constraint NoControlChars rejects control characters.

     @Component @Order(Ordered.HIGHEST_PRECEDENCE)
     public class CorrelationFilter extends OncePerRequestFilter {
         private static final Pattern VALID = Pattern.compile("[A-Za-z0-9._-]
     {1,64}");
         @Override protected void doFilterInternal(HttpServletRequest req,
     HttpServletResponse res, FilterChain chain)
                 throws ServletException, IOException {
                     String id = req.getHeader("X-Correlation-Id");
                     if (id == null || !VALID.matcher(id).matches()) id =
     UUID.randomUUID().toString();
             MDC.put("correlationId", id);
                     res.setHeader("X-Correlation-Id", id);
                     try { chain.doFilter(req, res); } finally { MDC.clear(); }
             }
     }

     public class UnknownParamInterceptor implements HandlerInterceptor {                //

         @Override public boolean preHandle(HttpServletRequest req,

     hm.getMethodAnnotation(AllowedParams.class);

     Set.of(allowed.value());

  The last rule is anyRequest().authenticated(), so unknown paths reach MVC and return
  404 as the API requires. The price of that choice is that a new endpoint without a rule
  would be open to any authenticated user. A build-time test, EndpointRuleCoverageTest,
  reads every controller mapping and fails if one has no explicit rule in the table.

  Rules that depend on data run inside services, after the lookup: a Cashier cancelling an
  IN_KITCHEN order gets 403 (API 9.5), and a Kitchen user at an unbound station gets 403
  on a ticket (the station comes from the ticket). For paths that carry the station id (K-01, X-
  01), StationAccess runs before any lookup:

     public void require(AuthenticatedUser user, long stationId) {
         if (user.role() == Role.MANAGER) return;
             if (!user.stationIds().contains(stationId)) throw
     ApiException.forbidden("Station not assigned to you");
     }


  Ordering note. In Spring the authentication filter runs before the MVC syntax checks
  (405, 415 and body parsing). For protected endpoints the real order is therefore 401, then
  the URL-level 403, then the rate limit, then 405, 415 and 400, and then validation. Section 8
  proposes updating API section 2.5 to match.

  3.9 Deadlock retry
  A deadlock is retried by running the whole transaction again. The retry must therefore sit
  outside the transaction: controllers call it, and the service method it wraps opens a fresh
  transaction on every attempt. Never call DeadlockRetry from inside a @Transactional
  method.

     @Component
     public class DeadlockRetry {
             private static final int MAX_RETRIES = 2;
             public <T> T run(Supplier<T> transactionalCall) {
                 for (int attempt = 0; ; attempt++) {
                             try { return transactionalCall.get(); }
                             catch (PessimisticLockingFailureException e) {
                     if (!isDeadlock(e) || attempt == MAX_RETRIES) throw e;
     // lock timeout (55P03) is not retried

                             }
                     }
             }

     final class SseSubscriber {
             private final SseEmitter emitter;
             private final BlockingQueue<SseEvent> queue;                                  // bounded at 100
             private final AtomicBoolean draining = new AtomicBoolean();


             boolean enqueue(SseEvent e) {

  the hash up and checks it, in this order: unknown or expired gives 401; consumed more
  than 10 seconds ago revokes the whole family and gives 401; consumed within the last 10
  seconds gives 401 without revoking (two tabs); otherwise it marks the token consumed
  and issues a new one in the same family. Deactivating a user, resetting a password and
  changing a password call revokeAllForUser.

  Edit (OrderEditService) is a transaction that begins with the order lock: lock the order;

  Putting the amount into the compare-and-set closes a race: the state check and the
  amount check happen in one atomic statement, so an order edited between the client's
  read and the payment can never be paid at its old total. When two payments race, the
  second UPDATE waits for the first transaction, finds the status no longer CREATED,
  updates zero rows, and explainFailedPayment turns that into 409
  PAYMENT_ALREADY_RECORDED.

  A cash payment's change is computed by PaymentValidator (tendered minus amount) and
  stored, so ck_payment_cash can check it. BillService adds each line's GST to a map keyed
  by rate and verifies that the rows sum to taxTotal and subtotal before returning; a
  mismatch is an INTERNAL_ERROR, because the CHECK constraints should have made it
  impossible.

  RefundService.createPendingIfPaid does nothing when the order has no payment;
  otherwise it inserts a REFUND_PENDING row, sets payment.status to
  REFUND_PENDING and audits REFUND_CREATED. complete locks the refund row,
  returns INVALID_TRANSITION when it is already REFUNDED, and otherwise sets
  REFUNDED on the refund and the payment.

  ix_orders_open. IN_KITCHEN tokens form the preparing list. READY tokens form the

         public static <T> List<Result<T>> run(int threads,
     IntFunction<Callable<T>> task) throws Exception {
             ExecutorService pool = Executors.newFixedThreadPool(threads);
             CountDownLatch ready = new CountDownLatch(threads), go = new
     CountDownLatch(1);
             List<Future<Result<T>>> futures = new ArrayList<>();
             for (int i = 0; i < threads; i++) {
                             Callable<T> c = task.apply(i);
                             futures.add(pool.submit(() -> {
                     ready.countDown(); go.await();
                     try { return Result.ok(c.call()); } catch (Exception e) {
     return Result.failed(e); }
                             }));
                     }
                     ready.await(); go.countDown();
                     List<Result<T>> results = new ArrayList<>();
                     for (Future<Result<T>> f : futures) results.add(f.get(30,
     TimeUnit.SECONDS));
             pool.shutdownNow();
             return results;
             }

  8.2 Proposed changes to the SAD, DBD and API
  SAD (for v0.2)

   1. Section 5.3: menuView holds one entry per filter combination (at most 64), not one
      entry.
   2. Sections 5.3 and 4.7: the board snapshot is cached for 1 second.
   3. Section 9: SNAPSHOT_REQUIRED carries reason SERVER_SHUTDOWN or OVERLOAD
        (when the event executor rejects work).
   4. Section 16.3: replace the state machine sketch with the two-step check of 4.4, so a
        missing rule gives 409 and an excluded role gives 403.

  DBD (for v0.2)

   5. S5 gains the condition AND total = :amount, so the state check and the amount check
        are one atomic statement (4.5).
   6. S3 returns the new quantity (RETURNING quantity), which lets the stock service
      detect depletion without a second read.
   7. PUT /orders/{id} replaces lines, so kf_app needs DELETE on order_line,
        order_line_modifier and order_line_component. A guard trigger keeps that safe, and
        DD-10 is amended to allow it. The same guard is attached to the two child tables
        through their order_line.
   8. Add statements S12b and S14.

     -- Guard for change 7: lines can be deleted only while the order is CREATED
     CREATE FUNCTION kf.guard_order_line_delete() RETURNS trigger LANGUAGE plpgsql
     AS $$
     BEGIN
         IF (SELECT status FROM kf.orders WHERE id = OLD.order_id) <> 'CREATED' THEN
         RAISE EXCEPTION 'order lines can be deleted only while the order is
     CREATED';
         END IF;
       RETURN OLD;
     END $$;
