  1. Introduction

  1.1 Purpose
  This document describes the architecture that satisfies KitchenFlow's requirements (KF-
  SRS-001): its structure, technology, runtime behaviour and data, and the cross-cutting
  concerns that keep it correct and fast under load: request pipeline, caching, rate limiting,
  concurrency control, security, reliability and observability. It is document 3 of 7. It is
  written at high-level-design depth, with low-level detail where the design is risky or subtle
  (sections 5, 6, 9 and 16). Documents 4 (database), 5 (API), 6 (low-level design) and 7
  (tests) refine it.


  1.2 Scope
  In scope: one restaurant outlet, one application server, one PostgreSQL database,
  browser-based clients and a reverse proxy. Out of scope: multi-outlet or multi-region
  operation, external integrations and hardware. The scale-out path is described in sections
  5.6 and 11 but is not built in version 1.

  3. Architecture overview

  3.1 Style
  KitchenFlow is a modular monolith: one deployable Spring Boot application, organised as
  feature modules with enforced boundaries, layered inside each module. Modules talk
  through small interfaces and in-process domain events. PostgreSQL is the only stateful
  component. The application itself keeps only three in-memory structures (the cache, the
  rate-limit buckets and the SSE connections), and all three are safe to lose on restart.

  3.4 Closed decisions
  UI (OI-02): React single-page app served by Nginx.

       The SRS already specifies a token-based REST API, CORS and generated OpenAPI. One
       API can then serve the web screens now and an Android kitchen display later.
       The live boards need client-side state and event handling whatever framework is used;
       server-rendered pages would duplicate that logic and mix session authentication with
       the JWT API.
       Fallback: if time is short, build the same screens in plain HTML and JavaScript (fetch
       plus a streaming reader). The API, the stream contract and the rest of this architecture
       do not change.

  Database (OI-03): PostgreSQL.

       Row-level locking (SELECT FOR UPDATE, SKIP LOCKED), partial indexes, RETURNING
       and percentile_cont map directly onto FR-KDS-06, FR-ORD-12 and FR-RPT-03.
       Strict constraints and transactional DDL support the integrity rules in SRS section 9.
       MySQL 8 would work for most requirements, but percentile reporting and partial
       indexes need workarounds.


  3.5 Container view
  Browser clients (cashier POS, station boards, manager board, status board and admin
  screens) reach the system through Nginx, which terminates TLS, serves the built UI as
  static files, applies coarse per-client rate limits and proxies /api to the application
  container. The application holds all business logic and talks to PostgreSQL over JDBC. An
  optional Prometheus and Grafana pair scrapes the application's metrics endpoint. Only
  Nginx is published to the network; the application and the database are reachable only
  inside the Compose network. Figure 1 shows the containers and their connections.

  5. Request pipeline, caching, rate limiting and load handling

  5.1 Request pipeline
  Every request passes the same ordered stages (Figure 3). Cheap, context-free checks run
  first, so that hostile or runaway traffic is rejected before it costs a database connection:
  size and connection limits and the per-IP limit at the edge, then correlation,
  authentication, per-user rate limiting, authorization and validation in the application. Rate
  limiting runs after authentication so that its key is the user, not just an address; login,
  which has no user yet, is limited by address and username. Business code, and the only
  database work, begins at stage 8.

  Login protection. The LOGIN bucket throttles attempts, and the lockout in FR-AUTH-06
  (5 failures in 10 minutes, locked for 15) is stored on the user row so it survives restarts.
  Both return the same generic message as a wrong password where applicable.

  Response contract. HTTP 429 with error code RATE_LIMITED, a Retry-After header in
  seconds and X-RateLimit-Remaining. Clients back off with jitter and never retry a write
  without its Idempotency-Key.

  Exemptions and safety. The health endpoint, static files and SSE heartbeats are not
  limited. A loadtest profile raises the limits for k6 runs; the application refuses to start with
  that profile when the production profile is active.

  Failure behaviour. The limiter has no external dependency. If it throws an unexpected
  error, requests fail open with an error log and a metric, except LOGIN, which fails closed.

  Observability and tests. A counter kf_rate_limit_rejected_total by class, and an alert
  when more than 5 percent of requests are rejected. Tests: the sixth login attempt returns
  429 even with the right password; buckets refill; one user's limit does not affect another's;
  the load test at design workload shows zero 429 responses.


  5.3 Caching
  Rule: cache for display and reference data; the database decides. Never cached: orders,
  tickets, payments, the stock figures used for decisions, and the audit log. Order validation
  and pricing always read current prices and availability from the database inside the
  transaction (BR-02, BR-04), so a stale cache can make a screen briefly out of date but can
  never sell an unavailable item or a wrong price. Configuration is the one cached decision
  input: it is evicted on change and expires after 60 seconds as a backstop.

  HTTP caching. GET /menu returns an ETag derived from a menu version counter that
  increments on every MenuChanged, with Cache-Control: no-cache, so screens revalidate
  cheaply and receive 304 when nothing changed. Built UI files have content-hashed names
  and Cache-Control: public, max-age=31536000, immutable; index.html is no-cache.

  Stampede and race handling. Caffeine's loading cache loads a key once even when many
  requests miss together. An eviction issued after commit runs after any in-flight load of
  that key finishes, because Caffeine computes each key atomically; a loader that read data
  from before the commit therefore cannot leave a stale entry behind. A race test in
  document 7 proves this, and the 5-minute expiry is the backstop.

  Staleness budget. The server reflects an availability change in the menu response as
  soon as the transaction commits (FR-INV-03). POS screens revalidate with the ETag
  whenever a new order is started and every 15 seconds.

  Measurement and sizing. Hit ratio, load time and size are exported through Micrometer;
  the target hit ratio for menuView is above 95 percent. A menu of 100 items is well under 1
  MB, so the three caches together use a few megabytes.

  5.5 Query efficiency
       No N+1 queries: fetch joins for an order with its lines, DTO projections for lists, and a
       test that counts statements per endpoint.
       Hibernate batching (batch size 50, ordered inserts) for order lines and ticket items.
       Offset pagination up to 100 rows per page; keyset pagination for deep order history.
       Reports aggregate in SQL over indexed ranges (section 8.5), inside read-only
       transactions with the report statement timeout.

  6. Concurrency and transaction design

  6.1 Principles
       PostgreSQL's default READ COMMITTED isolation, plus explicit locks where an
       invariant spans rows. SERIALIZABLE is rejected: it needs retry handling on every write
       path, costs throughput and is harder to explain.
       Optimistic locking (a version column) for a single row edited by people, such as a
       ticket; compare-and-set updates for state and counters; pessimistic row locks
       (SELECT FOR UPDATE) for invariants that span rows, such as an order and its tickets;
       unique constraints as the last line of defence.
       Short transactions: no network calls and no SSE sends inside one; events leave only
       after commit.
       One global lock order: the order row, then its tickets by id, then stock rows by item id.
       A fixed order prevents deadlocks.

  6.3 Why READY needs an order-level lock
  Two cooks bump the last two tickets of an order at the same moment. Without a lock,
  each transaction updates its own ticket row and then checks whether any ticket is still
  open. Under READ COMMITTED each sees the other's ticket as still in progress, because
  the other transaction has not committed. Neither sets the order READY, and it sits in
  IN_KITCHEN forever.

  The fix is to lock the order row (SELECT ... FOR UPDATE) at the start of every bump, recall
  and cancel. The second transaction waits until the first commits, then sees the first ticket
  DONE, counts zero open tickets and sets READY exactly once. Locking the order before
  the ticket gives a single lock order and so no deadlock. Describing the bug first and the fix
  second is the strongest way to tell this in an interview.

  6.5 Deadlocks, timeouts and retries
       lock_timeout of 2 seconds: a statement that waits longer fails with SQLSTATE 55P03
       and returns 503 SERVICE_BUSY with Retry-After (a proposed SRS error code, section
       15.2).
       Deadlock (40P01): the whole transaction is retried at most twice with a 20 to 60 ms
       jittered delay, only for operations that are safe to repeat.
       Optimistic conflicts are never retried automatically: the user decides, with the current
       state in the 409 response.
       Retries are counted in kf_db_lock_retry_total.

  6.6 Proving it
  Concurrency tests (NFR-CONC-01 to 04, AT-03 to AT-06) run against real PostgreSQL
  through Testcontainers. N threads are released together by a CountDownLatch and the
  assertions read the database: one order, stock exactly zero, one READY audit record.
  Each test repeats 50 times to expose flakiness. To prove the tests can fail, a mutation
  check removes each lock or constraint in turn and confirms that the matching test goes
  red.

  7.4 A station screen connects and reconnects
   1. The client opens the authenticated stream and starts buffering events.
   2. The server checks role and station binding, registers a subscriber and sends a hello
      event carrying server time.
   3. The client fetches the snapshot of the station's open tickets.
   4. The client merges the snapshot, then buffered and live events, keeping the highest
      version of each ticket.
   5. The server sends a heartbeat every 15 seconds.
   6. On disconnect the client reconnects with exponential backoff (1, 2, 4, 8 seconds, then
      15 at most, with jitter) and repeats steps 1 to 4.
   7. Safety nets: a full snapshot refresh every 60 seconds, and a 2-second snapshot poll
      while the stream is down.

  8.5 Reporting
  Reports aggregate in SQL over indexed ranges of at most 92 days. The business_day
  column is stored on orders so that date predicates stay indexable, and preparation-time
  statistics use percentile_cont. Reports run in read-only transactions with the report
  statement timeout and the report bulkhead (section 5.4). If reports ever slow down, a
  daily summary table refreshed by a scheduled job is the next step; it is not part of version
  1.


  8.6 Migrations and seed data
  Flyway applies versioned scripts. While the schema is still changing, keep a single baseline
  migration (V1) and replace it wholesale; after the first demo build, switch to forward-only
  incremental migrations (V2, V3 and so on). Seed data and the 100,000-order generator
  (SQL using generate_series) are separate profile-gated commands and never part of
  migrations.

  A nightly pg_dump in a Compose profile keeps 7 daily copies, and a restore is tested once
  before the demo. Targets for the demo: recovery point 24 hours, recovery time 15 minutes.
  Orders and audit records are kept for at least 12 months (DR-09). The only deletions in
  version 1 are idempotency records after 24 hours and refresh tokens after expiry.

  9. Real-time architecture (SSE)

  9.1 Why server-sent events
  Screens need one-way push from server to browser; their actions go back as ordinary
  REST calls. SSE runs over plain HTTP, passes proxies, reconnects automatically and needs
  no extra protocol. WebSocket would add a second protocol, a different authentication
  story and manual reconnection for no benefit here (ADR-03).

  9.3 Event design
  Each event carries the full current state of the object, not a difference, together with its
  version: for example a ticket with its id, status and version. The client keeps the highest
  version it has seen for each id, so processing is idempotent, independent of order and
  tolerant of gaps and duplicates. Events also carry a name and a per-process sequence id
  for debugging, but correctness never depends on replay.


  9.3a Hub design
       The SseHub keeps a concurrent map from stream key to subscribers. Each subscriber
       wraps an SseEmitter and a bounded queue of 100 events.
       After-commit listeners call publish(); a small bounded executor drains each queue and
       sends.
       A heartbeat comment every 15 seconds stops proxies closing idle streams and lets the
       server detect dead clients.




                                                                                                                              Page 28 of 45
System Architecture Document: KitchenFlow Restaurant Order & Kitchen Display System




       A subscriber is removed on completion, timeout or error. A subscriber whose queue
       overflows or whose send fails is closed, never skipped: the client reconnects and
       resynchronises, so an event is never silently lost.
       Connection caps and the SSE_CONNECT bucket apply (section 5.2). A gauge
       kf_sse_connections reports open streams by stream type.


  9.4 Consistency model
  The database is the truth and the push is a hint. Delivery happens after commit and is at-
  most-once. A screen stays correct because it resynchronises on connect, on reconnect,
  when told SNAPSHOT_REQUIRED (sent on graceful shutdown) and on a 60-second safety
  refresh. With a healthy stream, staleness equals the push latency (target under 1 second);
  with a failed stream the client polls the snapshot every 2 seconds.


  9.5 Authenticated streams in browsers
  The browser's EventSource cannot send an Authorization header, and putting a token in
  the URL would leak it into logs. Authenticated streams therefore use a fetch-based SSE
  client that sends the header; the public board uses plain EventSource. The server
  validates the token at connect and closes the stream when that token would expire (15
  minutes); the client refreshes the token and reconnects. A deactivated user's streams
  therefore end within 15 minutes, matching FR-AUTH-05.


  9.6 Proxy settings
  For /api/v1/stream/ Nginx uses HTTP/1.1, proxy_buffering off, proxy_cache off and
  proxy_read_timeout 3600s, and the application sends X-Accel-Buffering: no. Without
  these, events arrive in delayed batches, which is the most common SSE deployment bug.


  9.7 Multi-instance path
  Fan out through PostgreSQL LISTEN and NOTIFY (no new infrastructure) or Redis
  pub/sub; each instance feeds its own subscribers.

  10. Security architecture

  10.1 Trust boundaries
  Clients are untrusted. Nginx is the edge. The application trusts only what it has validated.
  The database accepts connections only from the application, over the Compose network,
  with least-privilege roles.


  10.2 Authentication
       Login issues a 15-minute access token (JWT) holding subject, role, bound stations and
       a token id. The signing key comes from the environment, is at least 256 bits and is
       never committed.
       Refresh tokens (Should): random, stored hashed, rotated on every use and delivered in
       an HttpOnly, Secure, SameSite=Strict cookie limited to the auth path. Reuse of a
       consumed token revokes the whole chain (FR-AUTH-07).
       Passwords use BCrypt with a cost chosen so hashing takes about 250 ms on the target
       machine. Wrong-user and wrong-password cases take similar time and return one
       message.
       Lockout counters live on the user row; the LOGIN bucket adds throttling (section 5.2).


  10.3 Authorization
  Four layers, deny by default: (1) URL rules by role; (2) method security on application
  services; (3) station binding in the ticket service; (4) the state machine, which checks the
  actor's role for each transition. AT-08 tests every role against every endpoint.

  11.2 Graceful shutdown
  The server shuts down gracefully with a 20-second grace period. On SIGTERM readiness
  goes down, new requests stop, in-flight transactions finish, and every stream receives
  SNAPSHOT_REQUIRED before it is closed.

  and migrations are applied. Compose health checks gate start-up order. Scheduled jobs:

  (hourly). Each is safe with one or many instances because it claims rows with SKIP

  16.3 Order state machine sketch

     enum OrderStatus { CREATED, PAID, IN_KITCHEN, READY, COMPLETED, CANCELLED }


     record Transition(OrderStatus from, OrderStatus to, Set<Role> roles) {}


     final class OrderStateMachine {
         private static final List<Transition> RULES = List.of(
             new Transition(CREATED,    PAID,       Set.of(CASHIER, MANAGER)),
                     new Transition(PAID,       IN_KITCHEN, Set.of(SYSTEM)),
                     new Transition(IN_KITCHEN, READY,      Set.of(SYSTEM)),
                     new Transition(READY,                               IN_KITCHEN, Set.of(KITCHEN, MANAGER)),




                                                                                                                             Page 42 of 45
System Architecture Document: KitchenFlow Restaurant Order & Kitchen Display System




                     new Transition(READY,                               COMPLETED,   Set.of(CASHIER, MANAGER)),
                     new Transition(CREATED,                             CANCELLED,   Set.of(CASHIER, MANAGER,
     SYSTEM)),
             new Transition(IN_KITCHEN, CANCELLED,                                    Set.of(MANAGER)));


             void check(OrderStatus from, OrderStatus to, Role actor) {
                 boolean allowed = RULES.stream().anyMatch(t ->
                         t.from() == from && t.to() == to && t.roles().contains(actor));
                     if (!allowed) throw new InvalidTransitionException(from, to);
             }
     }



  16.4 Bump sketch (lock order first)

     @Transactional
     public TicketView bump(long ticketId, long expectedVersion, Actor actor) {
         long orderId = tickets.orderIdOf(ticketId);          // plain read
         Order order = orders.lockForUpdate(orderId);          // SELECT ... FOR
     UPDATE, order first
         Ticket t     = tickets.get(ticketId);                                                   // read after the
     lock
             access.checkStation(actor, t.stationId());
             if (t.version() != expectedVersion) throw new StaleVersionException(t);
         t.transitionTo(TicketStatus.DONE, clock.instant());   // state machine
     guard
         if (order.status() == IN_KITCHEN && tickets.countOpen(orderId) == 0) {
             orderWorkflow.markReady(order, actor);                                             // compare-and-set
     plus audit
             }
             audit.record(actor, AuditAction.TICKET_BUMPED, t.id(), order.id());
             events.publish(new TicketChanged(t));                 // delivered after
     commit
         return TicketView.of(t);
     }
