  2. Problem and vision
  Quick service restaurants (QSRs) such as KFC, McDonald's and Burger King run on speed.
  A rush-hour order passes through the counter, the kitchen stations (fryer, grill, assembly,
  beverages) and the hand-over point, and every handoff is a place where orders get lost,
  delayed or duplicated. Paper KOT (kitchen order ticket) printers and shouting do not scale
  at peak hours: nobody can see which order is late, which item is out of stock, or how long
  preparation really takes.

  Vision: a backend-first system that takes an order at the counter, splits it automatically
  into station-level tickets, shows them live on kitchen screens, tracks each order until
  hand-over, and gives the manager timing and sales data afterwards.

  One-line pitch: an order-to-kitchen pipeline for a QSR outlet that takes the order, routes
  it to the right station, tracks it in real time, and measures how fast the kitchen really is.


  3. Domain background: how a QSR actually works
  Know these terms well enough to speak about them without notes.

       Order channels: counter POS, self-order kiosk, mobile or pickup app, delivery
       aggregators. Version 1 builds the counter channel, plus an optional simulated external
       channel.
       Order types: dine-in, takeaway, delivery.
       Token number: the customer gets a short token and watches a status board (Preparing
       or Ready).
       Station routing: each menu item belongs to a station, for example fries to the fry
       station, burgers to grill and assembly, drinks to beverages.
       Combos: one bill line (burger, fries, drink) becomes several station tasks.
       Modifiers: no onion, extra cheese, spicy. They must reach the cook accurately.
       KDS (Kitchen Display System): the screen that replaces paper KOT. Cooks start a
       ticket and bump it (mark it done) when finished; a recall undoes a bump.
       Expo (expeditor): checks that every part of an order is ready and hands it over
       together.
       86ing: marking an item unavailable when stock runs out, so the cashier cannot sell it.
       Timers and SLA: each ticket ages, and its colour (green, amber, red) shows how far it is
       past the target preparation time.

       Rush hours: lunch and dinner spikes, with many orders and many staff taps at the
       same moment. This is where correctness problems appear.
       Tax: GST on the bill, configured as a rate per item category.


  4. Goals and non-goals
  Goals

   1. Correctness under rush: no lost, duplicated or double-updated orders.
   2. Real-time visibility: a new order appears on the right station screen within about a
       second.
   3. A realistic order lifecycle with enforced state transitions and an audit trail.
   4. Measurable kitchen performance: preparation time per station, late orders, top items.
   5. Easy to run and demonstrate: one command to start, seeded data, a 5-minute demo.
   6. Defensible engineering: every design choice can be explained in an interview.

  Non-goals for version 1: real payment gateway, real aggregator integrations (Swiggy,
  Zomato), multi-outlet franchise management or multi-tenant SaaS, printer or POS
  hardware integration, demand forecasting, microservices or Kafka. Reason: one developer
  and limited time, and depth in a few things beats breadth.

  6. Product scope (MoSCoW)
  Must (the MVP the demo needs)

   1. Login with roles: Cashier, Kitchen, Manager, Admin.
   2. Menu: categories, items, modifiers, price, station mapping, availability toggle.
   3. Order entry: multiple items, modifiers, order type, token number generation.
   4. Order lifecycle with enforced transitions and cancellation rules.
   5. Automatic routing of order items into station tickets.
   6. KDS per station: live tickets, start, bump, recall, age timer.
   7. Customer status board: token with Preparing or Ready.
   8. Payment record (cash, UPI or card as simulated statuses) and a bill with GST.
   9. Order history with search, filters and pagination.
 10. Daily sales and kitchen timing summary.

  Should (what makes an interviewer lean forward)

       Combo items.
       Inventory-lite with automatic 86 at zero stock.
       Idempotent order creation.
       Audit log of every state change.
       Rush priority flag and late-order alerts.

  Could (only after everything else is solid)

       Simulated delivery-aggregator webhook, receipt PDF, an Android KDS client, an outlet
       id field for future multi-outlet use.

  Won't (this version): everything under non-goals above.


  7. Core user journeys
  A. Counter order (happy path). The cashier builds an order, the system validates items
  and availability, the order is created with a token, payment is recorded, and the order is
  accepted. It is routed into station tickets, the KDS shows them, cooks start and bump
  them, and when every ticket is done the order becomes READY. The status board shows
  the token, the order is handed over, and it is COMPLETED.

  B. Cancellation. Before preparation starts, the cashier can cancel and the tickets are
  removed. After preparation starts, a manager must approve, a reason is recorded, and the
  order is flagged as wastage.

  C. Item runs out. The manager marks an item as 86. The menu shows it unavailable and the
  cashier cannot add it; orders already placed are not affected.

  D. Kitchen mistake. A cook bumps the wrong ticket and recalls it. The ticket returns to in
  progress, and both actions are audited.

  E. Rush hour. Thirty or more orders arrive within a minute. There are no duplicates, tickets
  are ordered by arrival and priority, and every KDS screen stays in sync.

  State models

       Order: CREATED → PAID → IN_KITCHEN → READY → COMPLETED. CANCELLED is
       reachable from CREATED, PAID and IN_KITCHEN under the rules in journey B.
       Ticket: NEW → IN_PROGRESS → DONE. A recall moves DONE back to IN_PROGRESS.
       An order becomes READY only when all of its tickets are DONE.

  9. Quality targets (non-functional)
  These are targets to be validated by tests, not guesses.

       Correctness: retrying the same order request creates exactly one order. Two cooks
       acting on one ticket never corrupt its state.
       Performance: order placement p95 under 300 ms with 50 concurrent users on a
       laptop; a new ticket visible on the KDS within 1 second.
       Security: BCrypt-hashed passwords, role checks on every endpoint, no sensitive data
       in logs.
       Reliability: every state change inside a transaction; the app restarts without data loss;
       a KDS screen that reconnects reloads the current tickets.
       Observability: structured logs carrying the order id, plus health and metrics
       endpoints.
       Maintainability: layered code packaged by feature; at least 70% coverage on the
       service layer.
       Operability: a single docker compose command starts the app and database with seed
       data.

  13. Success criteria
       A new person can run the project with one command and the README.
       The 5-minute demo works: place orders at the counter, watch tickets appear on two
       station screens, bump them, see the status board change, and show the sales and
       timing report.
       All Must features work, and at least four showcase features from section 11 are
       implemented and tested.
       Every major design decision is recorded in one or two lines in the documents.
       You can answer the questions in section 14 without notes.
